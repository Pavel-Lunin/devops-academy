# DevOps Lab — черновик архитектуры

Статус: **черновик**. Ни приложения, ни инфраструктурных конфигов пока нет. Совместимость, команды и потребление ресурсов не проверялись; это план одного сквозного проекта, не выполненная lab.

## Назначение и границы

Маленький TypeScript HTTP API служит мишенью для Linux, сетей, контейнеров, мониторинга, CI/CD, автоматизации и восстановления. TypeScript уже знаком студенту; сложная бизнес-логика, мобильные клиенты, аутентификация, платежи и микросервисы не нужны. Используются только синтетические данные, без зависимости от TachoApp.

Первый вариант — один процесс и стандартные возможности выбранного Node.js; конкретные версии и способ работы с TypeScript определить при подготовке первого задания. Не добавлять framework/ORM только ради каркаса.

## Предлагаемая схема

```text
macOS / Apple Silicon — редактор, Git, клиент для проверки
  |
  | только явно разрешённый локальный доступ
  v
изолированная Linux ARM64 VM — основная мишень эксплуатации
  |
  +-- TypeScript HTTP API
  |     +-- позже: PostgreSQL с синтетической таблицей
  |     +-- вывод логов / позже: метрики
  |
  +-- позже: сбор метрик и локальные панели
  +-- позже: CI-агент и локальные артефакты
```

На раннем этапе API — процесс в Linux; затем та же функциональность переносится в контейнеры. База и служебные компоненты не должны публиковаться в LAN/Internet; разрешённый доступ с Mac ограничивается loopback и явно описанным пробросом. Точные порты, сети, volumes и bindings появятся в спецификации, не заданы в этом черновике.

Linux VM нужна для системного администрирования и сетевых опытов. Контейнерный вариант допустим для подходящих заданий после проверки runtime, но не заменяет systemd/полноценный Linux-хост во всех опытах. Изменять firewall, маршруты и DNS основного Mac не требуется.

## Предлагаемый контракт API

Это будущая спецификация, не существующие routes или реализованный код.

| Контракт | Назначение | Наблюдение |
|---|---|---|
| `GET /health` | Процесс жив, без проверки БД | Успешный ответ при работающем процессе |
| `GET /ready` | Готов принимать запросы | После добавления обязательной БД её недоступность делает readiness неуспешной, не меняя liveness |
| `GET /version` | Идентифицировать собранный артефакт | Версия и идентификатор сборки без секретов |
| Graceful shutdown | Завершать работу предсказуемо | Остановка процесса и закрытие соединений без зависания |
| Логи / позже метрики | Диагностировать сбой | Безопасные события запросов и ошибок, без токенов и персональных данных |

Позже — один простой доступ к PostgreSQL и восстановление синтетических данных. Точный формат ответов, timeout, status codes, проверка shutdown и негативные тесты задаются автором соответствующей lab, не реализуются сейчас.

## Постепенное развитие

| Этап | Добавление к тому же проекту | Будущее доказательство студента |
|---|---|---|
| A: Linux / сети | Процесс, локальный HTTP, логи и диагностика соединения | Отличить незапущенный процесс, неверный адрес и недоступный порт |
| A: контейнеры | Образ, Compose, затем PostgreSQL и отдельное состояние | Воспроизводимый запуск, сохранение данных и диагностика зависимости |
| A: ранний мониторинг | Метрики host/API, локальная панель, учебный сигнал | Обнаружить контролируемый сбой по наблюдениям |
| A: CI/CD | Преимущественно локальный Jenkins, проверки и артефакт, контролируемая доставка/возврат | Проследить сборку до версии и объяснить безопасный rollback |
| A: автоматизация / Kubernetes / IaC | Повторить конфигурацию, затем отдельные базовые сценарии | Повторяемость и диагностика без усложнения API |
| B | Углубления по утверждённой программе: Helm/GitOps, секреты, IaC, наблюдаемость | Интеграция и восстановление после управляемого инцидента |

Плановые недели, глубина и часы назначены в [индексе программы](../../curriculum/INDEX.md); фактическая среда и команды ещё не проверены. Kubernetes, CI и мониторинг не поднимаются одновременно с первым API; последующие среды включаются по потребности и лимитам машины. Локальные упражнения с IaC должны иметь бесплатный путь без реального облачного аккаунта; облачный запуск — только отдельным заданием и подтверждением расходов.

## Среда и критерий принятия архитектуры

Начальная гипотеза для одной базовой VM: 2 vCPU, 4 GiB RAM, диск 20 GiB. Это ориентир для обсуждения, **не измеренные требования**; Jenkins/БД/мониторинг/Kubernetes сюда автоматически не включены. До выбора среды выяснить доступную RAM/диск и проверить совокупный бюджет; предусмотреть облегчённый вариант.

Дальнейший автор должен оформить [спецификацию среды](../../templates/environment.md): Linux ARM64 и поддерживаемые версии, подтверждённые архитектуры образов/плагинов, runtime, лимиты CPU/RAM/диска, привязки сети, синтетические данные, способ остановки и точечную очистку. Не использовать непроверенный amd64-образ без замены или явно описанной эмуляции.

Архитектура принимается для первой lab только после проверки выбранной среды и независимых критериев. Перед publish/deploy, sudo, опасными операциями и сетевыми изменениями на хосте нужно отдельное подтверждение. Сценарии удаления не должны затрагивать общие volumes, личные файлы или другие проекты.
