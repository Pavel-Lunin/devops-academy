# A-M02-S01-L03 — Кому адресован кадр: Ethernet, MAC, ARP

- Статус: **проверено** для синтетических наблюдений; команды Linux и реальные интерфейсы не проверялись.
- Уровень: J0; W03.
- Prerequisite: [A-M02-S01-L02](A-M02-S01-L02-layers.md): кадр содержит IP-пакет, IP-пакет — транспортные данные; различать локальную и межсетевую доставку.

Эта тема нужна, чтобы не искать MAC удалённого сервера в локальной сети и не чинить приложение при незавершённом поиске локального соседа.

## Проверяемые цели

Объяснить различие IP и MAC; прочитать синтетическую таблицу соседей; выбрать, какие наблюдения нужны при отсутствии ARP-ответа, не меняя настройки Mac.

## Почему одного адреса недостаточно

**Ethernet** описывает доставку кадров в локальной среде. **MAC-адрес** обозначает интерфейс на канальном уровне; привычная запись — шесть шестнадцатеричных байтов, например `02:00:00:00:40:12`. Байт — восемь бит; шестнадцатеричная цифра кодирует четыре бита. Здесь достаточно узнавать формат, считать в этой системе не требуется. MAC не является постоянным паспортом устройства: бывают виртуальные и изменяемые адреса.

IP помогает определить конечное назначение и следующий участок пути. Когда ОС уже выбрала локальный следующий узел — **next hop**, ей нужен его MAC для Ethernet-кадра. Если получатель в той же IP-сети, next hop обычно он сам. Если в другой сети, next hop обычно локальный router — **gateway**, или шлюз. В этом уроке выбор next hop дан в условиях; как его вычислять по маске и таблице маршрутов — W04.

**ARP**, Address Resolution Protocol, сопоставляет IPv4-адрес локального соседа с MAC. При отсутствии записи узел отправляет запрос «у кого этот IPv4?». Ethernet-назначение запроса — `ff:ff:ff:ff:ff:ff`, то есть **broadcast**, рассылка всем участникам данного канального сегмента. В обычном обмене владелец адреса отвечает отправителю своим MAC; ОС временно сохраняет соответствие в **кэше соседей** — таблице уже полученных соответствий. Кэш может устареть, поэтому запись не доказывает доступность узла сейчас.

```text
IP назначения: удалённый S
локальный next hop: G
A -- ARP: кто G? --> Ethernet-сегмент
A <-- ответ G ------- G
A -- кадр к MAC G, внутри пакет к IP S --> G -- следующий участок --> S
```

Это обычный IPv4/Ethernet-случай. ARP-запрос не проходит через router по всему интернету. IPv6 использует другой механизм поиска соседей; его пакетный разбор пока не нужен. Коммутатор обычно изучает MAC по входящим кадрам и выбирает выход; при неизвестном назначении возможна рассылка по нескольким портам. Его таблица пересылки и ARP-кэш хоста — разные таблицы с разными задачами.

## Рабочая ситуация и ошибка

У учебного узла есть IP, но поиск MAC заданного шлюза не получил ответа. Возможны отключённый сосед, неверный адрес, неверное подключение или потеря кадров; одного отсутствующего ответа мало для выбора причины. Сначала сравни адрес next hop со схемой и доступные локальные наблюдения. Не начинай с перезапуска удалённого API: его запрос мог ещё не покинуть первый сегмент. Ошибка начинающего — ожидать MAC конечного удалённого сервера вместо локального шлюза.

## Эксперимент и собственная попытка

В [ENV-01](../../../labs/environments/ENV-01-offline-network.md) на отдельном маленьком примере два локальных соседа знают IP друг друга, но кэш пуст. Нарисуй три состояния: до запроса, запрос ко всем, ответ владельца; затем пометь, что повторный обмен может использовать кэш. Никакие реальные пакеты не отправляются.

Затем **точка 3** [lab](../../../labs/LAB-A-M02-S01-01-network-path/README.md): там удалённое назначение и противоречивая запись отчёта. Артефакт — таблица исходных данных, предположение о next hop и проверяемая гипотеза. Критерий: IP/MAC сопоставлены с исходной схемой, а влияние изменения входного факта объяснено.
