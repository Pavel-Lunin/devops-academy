# A-M02-S01-L02 — Как вложены данные и зачем уровни

- Статус: **проверено** для офлайн-примера; реальный захват пакетов не проводился.
- Уровень: J0; W03.
- Prerequisite: [A-M02-S01-L01](A-M02-S01-L01-participants.md): различать host, interface, switch и router; подтверждение проверяется вопросом, не наличием файла.

Уровни помогают назвать ответственность и выбрать наблюдение при отказе: физическое подключение, доставка между сетями, связь программ или содержимое запроса.

## Проверяемая цель

Разложить один пример на прикладные данные, транспорт, IP и локальную передачу; объяснить, что вложено во что; отличить наблюдение на одном уровне от доказательства работоспособности всего обмена.

## Как устроен обмен

Приложение формирует данные. В привычном HTTPS-запросе это смысл запроса, например запрос страницы. Протокол HTTPS использует HTTP и защиту TLS; детали HTTP/TLS пока не требуются. Дальше ОС обеспечивает передачу. **Транспортный уровень** связывает приложения: TCP передаёт упорядоченный поток байтов с механизмами восстановления потерь; UDP передаёт отдельные датаграммы с меньшим набором гарантий. Порт — числовое обозначение участника транспортного обмена на узле. Пока достаточно знать, что IP-адрес узла и порт приложения решают разные задачи.

**Сетевой уровень** использует IP-пакет для передачи между сетями. В нём есть адреса отправителя и назначения. **Канальный уровень** оформляет передачу в конкретной локальной среде: для Ethernet это кадр с MAC-адресами. **Физический уровень** — передача сигналов через среду: провод, оптику или радио. Реальные устройства могут реализовывать несколько функций.

**Инкапсуляция** означает вложение данных вместе со служебной информацией в оболочку следующего уровня. Заголовок — служебная часть перед полезной нагрузкой; у Ethernet есть также завершающая проверочная часть. Упрощённая схема одного фрагмента TCP-обмена:

```text
Ethernet-кадр [ MAC ... | IP-пакет [ IP ... | TCP-сегмент [ порты ... | данные ] ] ]
```

Сегмент — единица TCP; датаграмма — единица UDP. Нельзя считать один HTTP-запрос одним сегментом: данные могут разбиваться или объединяться при передаче. На получателе соответствующие уровни разбирают свои оболочки и передают данные выше. Router снимает локальную оболочку и создаёт новую для следующего участка; это не пересылка одного Ethernet-кадра через весь интернет. Изменения IP-полей при маршрутизации и преобразование адресов рассмотрим позже.

**TCP/IP** — семейство работающих интернет-протоколов и удобная модель: приложение, транспорт, интернет/IP, локальный канал. **OSI** — справочная семиуровневая модель: физический, канальный, сетевой, транспортный, сеансовый, представления, прикладной. Последние три часто обсуждают вместе в прикладной части TCP/IP. Соответствие не строго один к одному; это способ обсуждать функции, а не обязательные семь отдельных программ.

## Диагностика и ошибка

Горящий индикатор Ethernet означает лишь некоторое состояние физического соединения; он не доказывает правильные адреса и работу приложения. Обратный сигнал сильнее: полученные прикладные данные свидетельствуют об успешном обмене некоторым путём в тот момент. Но один успех не доказывает отсутствие периодических потерь. Начинающий часто делает вывод «кабель подключён — сеть исправна» без проверки остальных границ.

## Эксперимент и задача

В [ENV-01](../../../labs/environments/ENV-01-offline-network.md) запусти только авторский пример `layers`, если Python уже доступен. Он выводит вложенный словарь и названия оболочек; это не сетевой трафик и не проверка HTTPS. Если Python отсутствует, нарисуй ту же вложенность вручную; установка не требуется.

Самостоятельно выполни **точку 2** [lab](../../../labs/LAB-A-M02-S01-01-network-path/README.md), где вместо TCP задан другой транспорт и есть неполное наблюдение. Результат: таблица оболочек и два утверждения «что наблюдение подтверждает / что ещё неизвестно». Независимая проверка: ментор меняет одно наблюдение и просит пересмотреть только связанные выводы. Наличие красивой схемы само по себе не достаточно.
