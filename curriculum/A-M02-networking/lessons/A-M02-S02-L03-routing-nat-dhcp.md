# A-M02-S02-L03 — Путь из подсети: route, NAT и DHCP

- Статус: **проверено** в упрощённой офлайн-модели; изменение маршрутов и DHCP-сервер не запускались.
- Уровень: J0; W04.
- Prerequisite: [A-M02-S02-L02](A-M02-S02-L02-subnets.md): вычислить блок и проверить принадлежность адреса; [ARP](A-M02-S01-L03-ethernet-arp.md): next hop и MAC.
- Среда: [ENV-01](../../../labs/environments/ENV-01-offline-network.md), только синтетические таблицы и вычисления.

IP на интерфейсе не гарантирует путь к серверу. Нужно различить, кто выдал конфигурацию, кто выбирает маршрут и кто преобразует адреса; иначе любое сетевое нарушение легко ошибочно назвать «NAT не работает».

## Проверяемый результат

По простой таблице маршрутов выбрать интерфейс и next hop; объяснить default route; отличить выдачу конфигурации DHCP от routing и NAT; назвать, что ещё проверить, если адрес получен, а удалённый обмен не завершён.

## Выбор следующего участка

**Таблица маршрутов** связывает блок назначения с интерфейсом и, при необходимости, шлюзом. В упрощённой модели одного набора маршрутов сначала выбирается **самый длинный совпадающий префикс** — наиболее конкретный блок. `0.0.0.0/0`, **default route**, совпадает с любым IPv4 и служит последним вариантом. Это не адрес сервера и не синоним `127.0.0.1`.

```text
назначение             next hop       интерфейс
192.0.2.0/24           напрямую       e0
198.51.100.0/25        192.0.2.2       e0
0.0.0.0/0              192.0.2.1       e0
```

Для `198.51.100.13` совпадают `/25` и `/0`, выбирается `/25`. Для `203.0.113.9` остаётся `/0`. Шлюз в этом примере достижим напрямую в локальном сегменте: дальше ARP разрешает его IP в MAC. Маршрут «напрямую» означает доставку самому получателю на указанном интерфейсе, а не поиск ещё одного шлюза. Если совпадения нет, нельзя послать пакет по «интернету вообще»: нужно диагностировать отсутствие пути.

Авторская команда `python3 -B scripts/network_examples.py route` из корня Academy (macOS ARM64/Python3.9+) воспроизводит выбор первого назначения в этой таблице; ничего в ОС не меняет. Это модель **одной таблицы без равных конкурирующих префиксов**. Политики маршрутизации, метрики и несколько равных путей существуют, но здесь не моделируются. Выбор исходящего пути также не доказывает наличие обратного пути и разрешений на всех участках.

## NAT: преобразование, а не маршрут и не firewall

**NAT** изменяет IP-адреса при пересечении границы сетей. **NAPT**, часто называемый PAT, дополнительно меняет транспортные порты: несколько внутренних клиентов могут использовать один внешний адрес с разными отображениями. **Отображение** — сохранённая связь внутренней и внешней конечных точек для обратных пакетов. Пример: `10.200.0.7:42000 → 198.51.100.5:61000` на выходе; ответ на внешний адрес/порт связывается с внутренним клиентом. Не требуется запускать этот пример.

NAT сам по себе не выбирает все дальнейшие маршруты, не шифрует данные и не является полной политикой безопасности. Firewall — механизм разрешения/запрета трафика; его правила изучим отдельно. Из факта существования NAT не следует разрешение входящих соединений или исправность удалённого сервера.

## DHCP: как получают конфигурацию

**DHCP**, Dynamic Host Configuration Protocol, позволяет клиенту получить временную конфигурацию — адрес с арендой, маску и параметры вроде router/DNS. Аренда ограничивает срок использования адреса. При первоначальном получении часто описывают четыре сообщения: Discover — поиск сервера; Offer — предложение; Request — запрос выбранной конфигурации; ACK — подтверждение. **DNS** связывает имена с данными об адресах; подробности — следующий раздел. Передача такого параметра ещё не доказывает работоспособность DNS.

После ACK узел знает выданные параметры; это не тест доступа к интернету. Возможно, шлюз недоступен, удалённого маршрута нет, обратный путь нарушен или нужный обмен запрещён. Типичная ошибка — начать заново получать DHCP-адрес, не сравнив уже полученную конфигурацию с наблюдаемым путём.
