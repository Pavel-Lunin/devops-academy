# Диагностика сети Linux — шпаргалка

Дополнительная памятка по итогам вводного блока NET-01 в чате проекта Roadmap DevOps (15 ноября 2026). Это стартовые проверки и гипотезы, а не универсальный диагноз.

Проверяй путь последовательно: интерфейс и IP → маршрутизация → IP-связность → DNS → приложение.

## 1. Проверить интерфейс и адрес

```bash
ip -br addr
ip -4 addr show dev enp0s8
```

Проверь, что нужный интерфейс существует, поднят и имеет IP. Имя `enp0s8` замени на своё. Если IP отсутствует, выясни, должен ли он назначаться по DHCP или статически.

## 2. Проверить маршрут

```bash
ip -4 route
ip -4 route show default
ip -4 route get 1.1.1.1
```

В строке `default via 10.0.2.2 dev enp0s8` адрес после `via` — следующий узел, а `dev` — интерфейс. Если нет подходящего маршрута, это может объяснить недоступность внешней сети.

## 3. Проверить локальный шлюз и соседа

```bash
ping -c 4 10.0.2.2
ip -4 neigh
```

Замени `10.0.2.2` адресом своего шлюза. Ответ на ping подтверждает ICMP-связь со шлюзом, но не выход в интернет. Отсутствие ответа может быть связано с локальным соединением, шлюзом или фильтрацией ICMP. Состояния `FAILED` и `INCOMPLETE` в таблице соседей — диагностические подсказки.

## 4. Проверить внешний IP

```bash
ping -c 4 1.1.1.1
```

Если шлюз отвечает, а внешний IP нет, проверь маршрутизацию, NAT, фильтрацию и доступность внешней сети. Некоторые узлы фильтруют ICMP, поэтому неуспешный ping сам по себе не доказывает отсутствие доступа к интернету.

## 5. Проверить DNS

```bash
getent ahostsv4 example.com
cat /etc/resolv.conf
resolvectl status
```

`getent` проверяет разрешение имени системным механизмом. `/etc/resolv.conf` может указывать на локальный резолвер, поэтому его содержимое не всегда показывает конечный DNS-сервер. `resolvectl` применим в системах с `systemd-resolved`.

`Temporary failure in name resolution` указывает на сбой разрешения имени; проверь настройки и доступность DNS-сервиса.

## 6. Проверить HTTPS

```bash
curl -I https://example.com
curl -vI https://example.com
```

Первый запрос показывает HTTP-статус, второй — подробные этапы подключения, включая TLS.

| Сообщение | Первая гипотеза |
|---|---|
| `Could not resolve host` | DNS или разрешение имени |
| `Network is unreachable` | Нет подходящего IP-маршрута |
| `Connection refused` | Удалённый узел отклонил TCP-подключение |
| `Connection timed out` | Ответ на подключение не получен вовремя |
| `SSL certificate problem` | Проверка TLS-сертификата не прошла |

Это начальные гипотезы; для диагноза нужны дополнительные наблюдения.

## 7. Проверить локальный сервис и логи

```bash
ss -lnt
systemctl status systemd-resolved
journalctl -u systemd-resolved -b -n 30 --no-pager
journalctl -b -p warning --no-pager
```

`ss -lnt` показывает TCP-порты, которые слушает сервер. Если ожидаемый порт отсутствует, проверь запуск приложения и адрес, на котором оно слушает. Команды `systemctl` и `journalctl` здесь приведены для systemd; имя службы управления сетью зависит от дистрибутива. Общий журнал предупреждений может содержать много несвязанных событий.

## Короткий ответ на собеседовании

Если сервер не выходит в интернет, я проверю интерфейс и IP через `ip -br addr`, таблицу маршрутов через `ip route`, связь со шлюзом, затем внешний IP, разрешение имени через `getent` и HTTPS через `curl`. Если причина не ясна, проверю службу, порты, фильтрацию и журналы.
