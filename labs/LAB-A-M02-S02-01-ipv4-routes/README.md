# LAB-A-M02-S02-01 — Адрес, подсеть и следующий участок

Статус: **проверено** для офлайн-модели, без настройки Linux или Mac. J0; W04. Вход: [три урока S02](../../curriculum/A-M02-networking/SYLLABUS.md#a-m02-s02), подтверждённые основы S01; [ENV-01](../environments/ENV-01-offline-network.md).

Цель: рассчитать адреса, выбрать маршруты и сформулировать различимые гипотезы. Данные синтетические; к указанным адресам не подключаться. Для вычислительной сверки доступен Python 3.9+; установка Python для этой lab не предусмотрена.

## Часть 1 — Биты и категории, 60 мин

10 мин пример из L01, 35 своя таблица, 15 предъявление. Построй маски `/24`, `/26`, `/27` в двоичной и десятичной форме; посчитай полное количество адресов каждого блока. Объясни, почему из длины префикса не получается адрес gateway.

Классифицируй `10.24.9.130`, `172.31.4.5`, `172.32.4.5`, `127.0.0.1`, `203.0.113.8`: private RFC1918, loopback, документальный пример либо «не принадлежит этим трём категориям, нужны дополнительные сведения». Последняя категория не утверждает, что узел публично доступен. Объясни границу `172.16.0.0/12`, не суди только по первому октету.

Отрицательный кейс: в записи клиента из `10.24.9.0/24` gateway указан как `127.0.0.1`. Назови несоответствие роли адреса и безопасное следующее наблюдение; не исправляй конфигурацию.

## Часть 2 — Расчёт и неверная маска, 60 мин

10 мин пример `/27` из L02, 35 расчёт, 15 предъявление/сверка. Для `10.24.9.130/26` и `192.168.40.62/27` самостоятельно запиши сеть, маску, последний адрес блока, диапазон обычных host и число host. Для первого блока проверь принадлежность `10.24.9.190` и `10.24.9.192`.

Для отдельной арифметической сверки используется команда `python3 -B scripts/network_examples.py subnet АДРЕС/ПРЕФИКС`; параметр заменяется учебным адресом. Команда проверяет расчёт подсети, но не доступность узла или физическую сеть. При отсутствии Python вычисления выполняются по таблице вручную.

Диагностический кейс C1: A имеет `10.24.9.130/26`, B — `10.24.9.62/24`, оба подключены к одному учебному switch. Сравни, каким видит другого каждый узел: локальным или требующим router. Не утверждай автоматически, что связь невозможна: таблицы маршрутов и обратный путь полностью не даны. Предложи наблюдение для следующего шага.

## Часть 3 — Маршрут, выдача и преобразование, 60 мин

10 мин авторский пример `route` из L03, 35 свой разбор, 15 предъявление. Узел A: `10.24.9.130/26`, интерфейс `a0`. Таблица ниже — условные данные, не вывод `ip` или `netstat`:

```text
назначение             next hop       интерфейс
10.24.9.128/26         напрямую       a0
203.0.113.0/25         10.24.9.129     a0
0.0.0.0/0             10.24.9.190     a0
```

Выбери самый конкретный маршрут и next hop для `10.24.9.150`, `203.0.113.70`, `203.0.113.180`. Затем в **копии на бумаге** убери default route и повтори только последний выбор: что стало неизвестным/невозможным в рамках таблицы? Не менять таблицу маршрутов ОС.

Наблюдения: DHCP ACK выдал A его адрес, маску, router `.190`; внешнее NAPT-отображение записано как `10.24.9.130:45000 → 198.51.100.20:62000`; входящего ответа от удалённого узла пока не наблюдали. Объясни отдельно вклад каждого механизма и предел выводов.

Диагностический кейс C2: утверждают «раз есть ACK и NAT-запись, удалённый сервер точно отвечает». Дай две альтернативные гипотезы и различающее наблюдение. Одна запись преобразования не является захватом успешного ответа. Не требуется придумывать незнакомые команды.

## Независимая проверка

Артефакт: таблицы с промежуточными битами/границами, выбранный префикс и next hop по каждой цели, две аргументированные гипотезы для C1/C2. Критерии: расчёт совпадает со стандартной `ipaddress`, выбор пути — с исходной таблицей и сравнением префиксов; изменённый адрес и маска дают согласованные выводы. Калькулятор подтверждает арифметику, не физическую сеть.

Критерии полноты: каждое утверждение связано с исходным наблюдением; сеть не содержит host-битов, диапазоны не перекрываются; next hop выбран по маршруту, а не по похожему окончанию IP.
